# 알짜 글쓰기

어떤 에이전트가 쓰든 같은 품질로 글이 나오게 하는 절차다. 단계를 건너뛰지 않는다.

## 0. 먼저 읽기

- `.agents/product-marketing.md`: 블로그 방향, 독자, 말투, 다루지 않는 주제. 이 스킬의 규칙과 충돌하면 그 문서가 우선이다.
- `src/config.ts`의 `CATEGORY_ORDER`(쓸 수 있는 분야)와 `ADS.enabled`(쿠팡 링크 사용 여부)

## 1. 주제 확인

사용자가 주제를 주지 않았으면 `.agents/topic-backlog.md`의 "쓰는 법"대로 다음 주제를 고른다. `npm run post -- next`가 그 주제를 찾아 준다. 그 주제에 붙은 주의 사항도 읽는다.

다음 중 하나라도 걸리면 쓰지 않고 사용자에게 알린다. 사용자가 그 주제를 직접 지정한 경우만 예외다. 투자 권유는 예외 없이 금지다.

- 법률 해석·판단 (분쟁, 계약 해석, 누가 유리한지). 책임이 생기지 않는 행정 절차 안내는 괜찮다.
- 건강·의료 (증상, 약, 치료)
- 투자 권유 (어떤 주식·코인·상품을 사라)
- 중국 관련 내용 전부. 알리익스프레스·테무 등 중국 쇼핑몰, 중국 브랜드 제품 비교·추천도 포함한다.

사용자가 직접 지정해서 예외가 된 주제는 그 글에 한해 관련 표현 규칙(4번 "중국을 드러내는 표현" 등)도 함께 풀린다. 주제를 다루는 데 필요한 만큼만 쓴다.

그다음 확인한다.

- **검색 상황:** 이 글이 `.agents/product-marketing.md`의 "검색하는 상황 7가지" 중 무엇을 노리는지 한 줄로 정한다.
- **분야:** `CATEGORY_ORDER`에 있는 분야만 쓴다. 맞는 분야가 없으면 새로 만들지 말고 사용자에게 묻는다.
- **중복:** `grep -ril "<핵심 키워드>" src/content/posts`로 같은 주제의 글이 있는지 본다. 있으면 새 글 대신 기존 글을 갱신한다 (7번).
- **시기:** 명절·시즌 주제는 검색이 몰리기 최소 2~4주 전에 발행돼 있어야 한다.
- **더하는 것:** 그 검색어의 상위 결과를 읽고, 우리 글이 그 글들에 없는 무엇을 더하는지 한 문장으로 적는다 (더 최신 숫자, 조건별 표, 더 분명한 답 등). 그 문장을 쓸 수 없으면 쓰지 않고 사용자에게 알린다.

## 2. 웹 리서치

**AI 모델이 알고 있는 지식으로 쓰지 않는다.** 금액, 요율, 기한, 일정, 조건은 전부 지금 웹에서 확인한다. 웹 검색·페이지 읽기 도구가 없으면 쓰지 말고 사용자에게 알린다.

출처는 이 순서로 찾는다.
1. 공식 기관: 정부·공공기관(정부24, 국세청, 고용노동부 등), 해당 기업의 공식 공지·고객센터
2. 언론 기사 (날짜 확인)
3. 유튜브: 사용자가 주제를 직접 준 경우에만, 조회수가 많고 믿을 만한 영상만. 영상 속 숫자도 1·2번 출처와 맞춰 본다.

규칙:
- 출처가 불분명한 블로그·커뮤니티 글은 근거로 쓰지 않는다.
- 나무위키처럼 누구나 고칠 수 있는 곳은 단서 찾기에만 쓴다. 그 내용은 1·2번 출처에서 다시 확인한 뒤 쓴다. 확인되지 않으면 쓰지 않는다.
- 출처마다 숫자가 다르면 공식 기관을 따른다. 그래도 불분명하면 그 내용을 빼거나 사용자에게 묻는다.
- 기간이 정해진 정책·혜택은 적용 기간을 반드시 확인한다.
- 확인한 출처마다 기관명, 문서 제목, 링크, 확인 날짜를 적어 둔다 (6번 출처 목록에 쓴다).

## 3. 파일 만들기

`src/content/posts/<파일명>.md`. 파일명이 곧 주소(`/posts/<파일명>/`)다. 초안은 이 명령으로 만든다. `draft: true`와 TODO가 들어 있으니 발행 전에 모두 없앤다:

```bash
npm run post -- new <파일명> --title "제목" --category 분야
```

- 파일명은 영문 소문자와 하이픈만 쓴다. 예: `coupang-alba-pay`, `onnuri-gift-card-discount`
- 해마다 반복되는 주제는 파일명에 연도를 넣지 않는다. 연도는 제목에만 넣고, 다음 해에는 같은 파일을 갱신한다. 주소가 그대로여야 검색 순위가 이어진다.
- 이미 발행된 글의 파일명은 절대 바꾸지 않는다.

frontmatter (형식이 틀리면 빌드가 실패한다):

```yaml
---
title: "온누리 상품권 할인율 (2026): 구매 한도·사용처·환불까지 총정리"
description: "2026년 디지털온누리상품권 할인율은 ○%, 월 구매 한도는 ○만원입니다. 사용처와 환불 방법까지 정리했습니다."
date: 2026-10-28
category: "혜택"            # CATEGORY_ORDER에 있는 것만
tags: ["온누리상품권", "추석"]   # 명절·시즌은 태그로
summary: "한두 문장으로 된 바로 그 답. 숫자를 넣는다."
faq:
  - q: "독자가 실제로 검색할 법한 질문"
    a: "짧고 분명한 답"
ogTitle: "공유 이미지용 짧은 제목\n줄바꿈 가능"   # 선택
---
```

- **title:** 후보를 5개 이상 써 보고 가장 강한 것을 고른다. 해당 연도나 다가올 연도를 넣는다. 형식은 "(2026)", "2026년", "2026:" 모두 된다. 독자가 검색창에 칠 말을 앞쪽에 둔다. "총정리"는 써도 된다.
- **description:** 1~200자 (스키마 제한). 80~120자 안에서 답의 핵심 숫자를 보여 준다.
- **summary:** 글 맨 위에 나오는 답. 이것만 읽어도 검색한 이유가 풀려야 한다.
- **faq:** 3~5개. 본문을 그대로 반복하지 말고 본문에서 다루지 않은 곁가지 질문을 넣는다. 구조화 데이터로도 나간다.
- **date:** 발행일. **updated:** 갱신할 때만 넣는다.
- `draft: true`이면 사이트에 나오지 않는다.

## 4. 본문 쓰기

구조:
1. 첫 줄에 기준일 인용문: `> 2026년 10월 28일 기준입니다.` 기간이 정해진 정보면 적용 기간도 쓴다: `> 2026년 10월 28일 기준이며, 이 할인은 2026년 12월 31일까지입니다.`
2. 쿠팡 링크가 있는 글이면 기준일 바로 아래에 고지문 (5번)
3. `##` 소제목 섹션 2개 이상. 제목(h1)은 frontmatter가 만들므로 본문에 `#`을 쓰지 않는다. 본문 중간 광고가 두 번째 `##` 앞에 자동으로 들어간다.
4. 맨 끝에 `## 출처` (6번)

쓰는 법:
- 결론과 숫자를 먼저 쓴다. 서론으로 시작하지 않는다.
- 비교·조건·금액은 표로 정리한다. 독자 대부분이 휴대폰이라 표는 5열 이하로 만든다. 절차는 번호 목록으로 쓴다.
- 조건별로 나눠 답한다 (야간이면, 주말이면, ○○카드면). 예외 상황은 분명히 적는다.
- 숫자는 단위와 기준까지 정확하게 쓴다. 공식 명칭은 처음 나올 때 함께 적는다. 예: 온누리 상품권(정식 명칭: 디지털온누리상품권)
- 인용문(`>`)은 기준일, 고지문, 꼭 필요한 주의 한두 개에만 쓴다.
- 굵게(`**`)의 닫는 `**` 바로 앞이 괄호·따옴표·% 같은 문장부호이고 바로 뒤에 한글이 붙으면 굵게가 적용되지 않고 `**`가 그대로 보인다. `**11월 19일(목)**이고` 대신 `**11월 19일**(목)이고`처럼 문장부호를 굵게 밖으로 뺀다.

순위·추천 글 (맛집, 제품 TOP 5, "추천" 등):
- 체험 없이 맛·사용감으로 순위를 매기지 않는다. "1위", "최고" 같은 주관적 순위 표현을 쓰지 않는다.
- 대신 확인 가능한 기준으로 고르고, 그 기준을 글 앞쪽에 밝힌다. 예: 공공기관 지정·선정, 언론 소개, 공식 스펙(용량·소비전력·가격), 업력.
- 고른 대상마다 같은 항목을 표로 비교한다. 독자가 자기 조건에 맞게 고를 수 있게 한다.
- 기준을 채울 출처가 부족하면 쓰지 않고 사용자에게 알린다.

말투 (자세한 건 `.agents/product-marketing.md`의 Brand Voice):
- 기본은 "합니다·입니다". "-요"는 FAQ 답과 짧은 팁에서만 쓴다. 한 문단·표·목록 안에서 어미를 섞지 않는다.
- 과장(역대급, 무조건, 꿀팁 대방출, 모르면 손해)과 서론 상투어("오늘은 ○○에 대해 알아보겠습니다")를 쓰지 않는다.
- 하지 않은 경험을 한 것처럼 쓰지 않는다 ("직접 가 보니", "써 보니", "제가 해 보니").
- 글 안에도, 사이트 어디에도 AI가 썼다는 말을 넣지 않는다.
- 중국을 드러내는 표현을 쓰지 않는다.

## 5. 쿠팡 파트너스 링크

- `src/config.ts`의 `ADS.enabled`가 `true`(AdSense 승인 후)면 쿠팡 링크를 넣지 않는다.
- 제품을 고르거나 사는 글(쇼핑 분야 등)에서 자연스러울 때만 넣는다. 억지로 넣지 않는다.
- 링크는 마크다운 대신 HTML로 쓴다. 검색엔진에 광고 링크임을 알리기 위해서다:
  `<a href="https://link.coupang.com/a/..." rel="sponsored nofollow">제품명 보기</a>`
- 링크가 하나라도 있으면 기준일 바로 아래에 이 고지문을 그대로 넣는다 (공정위 추천·보증 심사지침):
  `> 이 포스팅은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.`

## 6. 출처 목록

본문 맨 끝 `## 출처`에 2번에서 확인한 출처를 적는다.

```markdown
## 출처

- 국세청, [연말정산 미리보기 안내](https://...) (2026-10-28 확인)
- 고용노동부, [2026년 최저임금 고시](https://...) (2026-10-28 확인)
```

- 공식 기관과 언론만 적는다. 나무위키 같은 곳은 참고했더라도 적지 않는다.
- 링크가 실제로 열리는지 확인한다.

## 7. 기존 글 갱신

- 파일명(주소)은 그대로 둔다.
- 2번 리서치를 다시 하고 숫자·기간·출처를 새로 확인한다.
- `updated:`에 오늘 날짜를 넣고, 기준일 인용문과 출처의 확인 날짜를 바꾼다.
- 해가 바뀌는 글은 title의 연도를 바꾼다.
- 바뀐 내용을 알릴 필요가 있으면 기준일 아래에 사실만 짧게 쓴다. 예: `> 2027년 1월 1일부터 시급이 ○원으로 바뀌어 반영했습니다.`

## 8. AI 말버릇 제거 (반드시 외부 스킬 2개로)

다 쓴 글의 AI 말버릇은 직접 고치지 말고 **copy-editing → humanize-korean** 순서로 걸러 낸다. 둘 중 하나라도 설치나 실행을 할 수 없는 환경이면 발행하지 말고 사용자에게 알린다.

### 8-1. copy-editing

**copy-editing 스킬**(coreyhaines31/marketingskills)로 글 전체를 한 번 거친다.

- 스킬이 없으면 먼저 설치한다. `<agent>`에는 자기 에이전트 이름(claude-code, codex, cursor 등)을 넣는다:
  ```bash
  npx skills add coreyhaines31/marketingskills --skill copy-editing -a <agent> -y
  ```
- 그 스킬로 글 전체를 한 번 거친다. 어미가 섞인 곳도 함께 본다.
- 스킬이 숫자, 사실, 출처, 기준일을 바꾸면 되돌린다. 문장만 다듬는다.

### 8-2. humanize-korean

copy-editing은 영어 기준이라, 번역투와 한국어 문장 리듬은 **humanize-korean 스킬**(epoko77-ai/im-not-ai)로 잡는다.

1. 스킬이 없으면 프로젝트 안에 설치한다. Codex면 `claude` 대신 `codex`를 쓴다. git에는 올라가지 않는다:
   ```bash
   bash .agents/setup-humanize-korean.sh claude
   ```
   Claude Code는 새로 설치한 뒤 세션을 다시 시작해야 전용 에이전트가 잡힌다.
2. 저장소 루트에서 글 파일을 **정밀 모드**로 돌린다. 입력 텍스트로 아래 조건을 함께 준다:
   ```text
   src/content/posts/<파일명>.md 장르: 블로그 강도: 보수 --strict
   frontmatter 키·date·category·tags, 표, 인라인 코드, 소제목, 링크 URL, ## 출처 목록은 그대로 둔다.
   어미는 합니다·입니다, faq 답변만 -요를 유지한다. 법률 조문, 판결 내용, 숫자, 날짜, 금액, 기관명은 바꾸지 않는다.
   ```
3. 스킬은 `_workspace/`의 사본만 고친다. 게이트(`verify_gates.py`)가 `gate: OK`인 결과만 쓴다. 경고면 해당 항목을 확인하고, 중단이면 그 결과를 버린다.
4. 사본과 원문을 비교해 숫자, 표, 소제목, 출처가 같은지 확인한다. 바뀐 문장은 직접 읽고 뜻이 달라진 곳을 되돌린다. 조건, 상한, 예외를 나타내는 문장을 특히 본다.
5. `final.md` 끝의 `<!-- HUMANIZE-SUMMARY -->` 블록을 지운 본문을 글 파일에 반영한다.

등급 B는 실패가 아니다. 잘 쓴 글은 변경률이 낮아서 B가 나온다. 판단 기준은 S1 잔존 0건과 게이트 통과다.

## 9. 발행 전 검사

먼저 빌드하고 `npm run post -- check <파일명> --links`를 돌려 오류를 0개로 만든다. "확인" 항목은 사람이 판단할 내용이니 하나씩 읽는다. 사실 확인과 스킬 실행 여부는 이 명령이 대신하지 않으므로 아래 목록을 직접 확인한다.

- [ ] 다루지 않는 주제에 걸리지 않는다 (1번)
- [ ] 모든 숫자·기간이 이번에 웹에서 확인한 출처와 맞는다
- [ ] title에 연도가 있다. description은 200자 이하다
- [ ] 첫 줄에 기준일이 있다. 기간이 정해진 정보면 적용 기간도 있다
- [ ] summary만 읽어도 답이 된다
- [ ] 쿠팡 링크가 있으면 고지문이 있고 링크에 `rel="sponsored nofollow"`가 있다
- [ ] 끝에 `## 출처`가 있고, 공식 기관·언론만 있다
- [ ] 체험담 표현, AI 작성 언급, 중국 관련 내용이 없다 (사용자 지정 예외 제외)
- [ ] 순위·추천 글이면 고른 기준을 밝혔고 주관적 순위 표현이 없다
- [ ] copy-editing 스킬을 거쳤다
- [ ] humanize-korean 정밀 모드를 거쳤고, 게이트가 통과했고, 숫자·표·출처가 그대로다
- [ ] 빌드된 페이지에 `**`가 글자 그대로 보이는 곳이 없다 (`grep -c '\*\*' dist/posts/<파일명>/index.html` 결과가 0). draft 글은 페이지가 만들어지지 않으니 잠시 `draft: false`로 빌드해 확인하고 되돌린다

## 10. 빌드와 발행

1. 빌드 검사 (Node 22.23.4 이상 필요):
   ```bash
   npm run build
   ```
   "Node.js ... is not supported" 오류가 나면 `HANDOFF.md`의 명령어 항목대로 더 새 Node로 실행한다. 그 밖의 오류는 고치고 다시 빌드한다. 빌드가 통과하지 않은 글은 발행하지 않는다.
2. 글 파일만 커밋한다. 백로그 주제였으면 `.agents/topic-backlog.md`의 상태 변경도 같은 커밋에 넣는다. 메시지는 새 글이면 `글: <title>`, 갱신이면 `글 갱신: <title>`.
3. main에 푸시하면 Cloudflare Pages가 자동으로 빌드·배포한다. 푸시 권한이 없거나 사용자가 발행까지 맡기지 않았으면 커밋까지만 하고 알린다.
